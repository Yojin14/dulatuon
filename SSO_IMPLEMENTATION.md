# SSO OAuth2 Implementation

This document describes the SSO (Single Sign-On) OAuth2 implementation that has been copied from the finance.citycollege project and implemented in hive.citycollege.

## Overview

The SSO implementation uses OAuth2 authorization code flow to authenticate users through an external OAuth2 server (AIMS). Users can log in using their AIMS credentials, and the application will automatically create or update their local user account.

## Environment Configuration

Add the following environment variables to your `.env` file:

```env
# OAuth2 / Passport Configuration
PASSPORT_CLIENT_ID=your_oauth_client_id
PASSPORT_CLIENT_SECRET=your_oauth_client_secret
PASSPORT_REDIRECT_URI=http://localhost:3000/auth/callback
PASSPORT_SERVER_URI=http://your-oauth-server.com
```

### Configuration Details:

- **PASSPORT_CLIENT_ID**: The OAuth2 client ID provided by the OAuth2 server
- **PASSPORT_CLIENT_SECRET**: The OAuth2 client secret provided by the OAuth2 server
- **PASSPORT_REDIRECT_URI**: The callback URL where the OAuth2 server will redirect after authorization (must match the URL registered with OAuth2 server)
- **PASSPORT_SERVER_URI**: The base URL of your OAuth2 server (without trailing slash)

## How It Works

### Login Flow

1. User clicks "Login with AIMS" button on login page
2. User is redirected to OAuth2 server (`/oauth/authorize`)
3. User authenticates on OAuth2 server
4. OAuth2 server redirects back to `/auth/callback` with authorization code
5. Application exchanges authorization code for access token
6. Application stores tokens temporarily in session
7. Application redirects to `/auth/connect-user`
8. Application fetches user data from OAuth2 server using access token
9. Application creates or updates local user record with:
   - Email
   - Name
   - Random password (SSO users don't use local passwords)
   - Access token
   - Refresh token
10. User is logged in and redirected to dashboard
11. Session tokens are cleared after successful login

### Logout Flow

1. User clicks logout
2. Custom LogoutResponse calls `user->logoutFromSSO()`
3. Application sends logout request to OAuth2 server
4. SSO tokens are cleared from user record
5. User is logged out locally
6. Session is invalidated

## Security Features

- **State Parameter**: Random state parameter is generated and sent with authorization request to prevent CSRF attacks
- **Token Storage**: Access tokens and refresh tokens are stored securely in the database
- **Fallback Authentication**: If Basic Auth fails, the application tries form-based authentication
- **Error Handling**: Comprehensive error logging and user-friendly error messages
- **Password Security**: SSO users are assigned random passwords, preventing local password-based login

## API Endpoints Required on OAuth2 Server

Your OAuth2 server must provide the following endpoints:

1. **Authorization Endpoint**: `/oauth/authorize`
   - Accepts: client_id, redirect_uri, response_type, scope, state
   - Returns: authorization code

2. **Token Endpoint**: `/oauth/token`
   - Accepts: grant_type, client_id, client_secret, redirect_uri, code
   - Returns: access_token, refresh_token, token_type

3. **User Endpoint**: `/api/user`
   - Accepts: Authorization Bearer token
   - Returns: User data (must include email and name)

4. **Logout Endpoint**: `/api/logoutsso`
   - Accepts: Authorization Bearer token
   - Returns: Success response

## Testing

### Test SSO Configuration

Visit `/auth/test-sso` to verify your OAuth2 configuration. This endpoint returns:
- Client ID (visible)
- Redirect URI (visible)
- Server URL (visible)
- Client secret status (whether it's set, not the actual value)
- Session token status

### Manual Testing Flow

1. Ensure your `.env` variables are set correctly
2. Visit the login page
3. Click "Login with AIMS"
4. You should be redirected to the OAuth2 server
5. After successful authentication, you should be redirected back and logged in
6. Check the logs for any errors during the process

- SSO tokens are stored as `longText` to accommodate large token strings

- The UI seamlessly integrates SSO login with the existing authentication system
- Users created via SSO are automatically assigned random passwords

## Troubleshooting

### Common Issues

1. **"Authorization failed: No code returned"**
   - Check PASSPORT_CLIENT_ID is correct
   - Verify PASSPORT_REDIRECT_URI matches the registered callback URL

2. **"SSO Login Failed"**
   - Check PASSPORT_CLIENT_SECRET is correct
   - Verify OAuth2 server is accessible
   - Check logs for detailed error messages

3. **"No access token found in session"**
   - Session might have expired
   - Check session configuration in Laravel

4. **"Invalid user data received from SSO server"**
   - Verify OAuth2 server returns email and name fields
   - Check `/api/user` endpoint response format
